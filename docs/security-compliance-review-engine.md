# Security and compliance review engine (MVP 2, W3–W5)

`SecurityReviewService.review(request, token, progress, selectedModelId?)` performs a read-only review of a Git commit. It supports `scope: "changes"` (base → target, with access to other files at target) and `scope: "branch"` (files tracked at target). `categories` can include `security`, `compliance` or both. The `targetSha`, optional `baseSha`, and policy content hash are resolved before requests to the model; changing the checked-out branch does not change a running review.

The survey groups files by component (up to 8 per model request, 256 per run), reports files outside the budget, and loads compliance rules from the policy in the target commit. The model may request bounded `read_file`, `search_code`, `file_exists` and `read_diff` operations; it cannot run shell commands. Review uses the selected Copilot model through the existing VS Code language-model API. Work exceeding model or tool limits is reported as incomplete.

Every returned finding must cite a real file, revision and line. In changes mode, its cited line must be added or removed by the comparison. Compliance evidence must also lie inside the cited rule's scope. A second model request checks candidates for counterevidence, with the rule's description and required evidence for compliance findings: rejected candidates are discarded, uncertain ones remain hypotheses, and a candidate the verifier returns no verdict for is a hypothesis and makes coverage incomplete. Findings for `manual` or `static` rules are never promoted to `verified` by the AI check. A `verified` status means the citation passed mechanical validation **and** the second AI check supported the finding; it is not a proof of exploitability. Review coverage records surveyed, analyzed, skipped and failed files separately and never infers that no vulnerabilities exist from an empty findings list.

Each component is analyzed and verified in turn, and its outcome (kept findings with their status, policy results, partly reviewed files, model notes) is saved by `ReviewUnitCache` (`reviewUnitCache.ts`) in workspace state. The key hashes the model id and version, `PROMPT_VERSION` (a hash of the prompts and the initial content limits), any extra instructions, both commits, scope, categories, the component's paths and its rules, so a saved outcome is reused only when the model would be asked exactly the same thing. Only components with no failed check are saved. At most 300 outcomes are kept, none older than 30 days, newest first. A review run again at the same commits therefore asks only for components that are not saved yet: a review stopped by Cancel, by closing VS Code or by a model error continues where it left off.

Cancel stops after the current step. When at least one component finished, the result is returned with `partial: { unitsDone, unitsTotal }`, incomplete coverage and a limitation saying where it stopped; the dashboard shows and saves it like a finished review, with **Continue review**. Cancelled before any component finished, the review fails as cancelled. A review superseded by another one, or by closing the panel, is dropped as before.

Model notes become `toVerify`: what someone should check by hand, such as callers or CI settings outside the scope. `consolidateLimitations` keeps each note whole (a sentence like "the severity depends on that configuration" stays with the one before it), drops restatements the report already makes (which files were in scope, that they contain no sinks, that no flaw was found, that a file was not read, truncation), keeps a "was not read" sentence only beside a point it explains, and never re-capitalizes file names. `limitations` keeps the tool's own notes. Coverage is summarized once (`summarizeCoverage`) as fully reviewed, partly reviewed (with lockfiles, images, diagrams and test inputs counted apart), not reviewed and failed checks.

Compliance rules with `verification: "manual"` or `"static"` are marked `insufficient_evidence` until their corresponding evidence or scanner exists. Missing policy is `not_configured`. A rule the model judges not applicable in every reviewed batch is `not_applicable`. A rule cannot pass when applicable files or checks fail or exceed the review budget. Security review does not require a policy. Dependency vulnerability databases and build/test execution are outside the engine.

## Review skills and clean code

A review skill is a short checklist sent to the model with the files it applies to. The extension ships eight in `resources/review-skills/`, written for this extension from public standards and naming them in `references`: injection and dangerous sinks (CWE Top 25, OWASP ASVS 5.0), authentication and sessions (ASVS), secrets and cryptography (Microsoft SDL, ASVS), CI/CD and supply chain (OpenSSF Scorecard, SLSA), cloud and infrastructure as code (AWS Well-Architected Security Pillar), Python and JavaScript/TypeScript (Amazon Q detector library categories, CWE), and clean code (Google's code review guide). A skill file is Markdown with a header between `---` lines: `id`, `name`, `category` (`security` or `quality`), `appliesTo` (a JSON array of globs) and optional `references`, then the guidance (`parseReviewSkill` in `services/reviewSkills.ts`).

`ReviewSkillStore` (`reviewSkillStore.ts`) adds the skills a user imports from a Markdown file (at most 30, 6,000 characters of guidance each; one with a bundled id replaces it) and the ones turned off, both in global state. Skills are never read from the reviewed repository: the prompt treats them as trusted guidance, and repository content stays untrusted. For each component, `selectReviewSkills` picks the enabled skills whose globs match one of its paths, security skills when `security` is reviewed and quality skills when `quality` is, up to 8,000 characters; a skill that does not fit is reported as left out. A hash of the guidance sent is part of the component's cache key, so turning a skill off or changing one asks the model again for the components it applied to. The result lists the skills per component (`skillsApplied`), and a finding may name the skill that led to it (`skill`, kept only when that skill was sent for its component).

`categories` may also include `quality` (the dashboard's **Clean code** checkbox, off by default and remembered). Quality findings cover maintainability: complexity, duplication, naming, error handling, dead code and tests. Their severity is at most medium, they go through the same evidence and second-check rules, and `assessReadiness` keeps them in their own `quality` list: they never make a review blocked or needing attention. The report has a **Code quality** section and a **Review skills** section.

## Dashboard and release review (W6–W7)

`ReviewController` connects the engine to the dashboard. A review is a diff (`scope: "changes"`) or every file at a commit (`scope: "branch"`); each starts at once with both categories and the model selected for AI summaries; there is no dialog. The entry points are:

- **Review commit** in the detail toolbar, next to **Summarize changes**: the changes the detail pane shows (the selected commit against its parent, or the loaded Base/Target selection, branch comparison or release range);
- the history menu: a commit against its parent, or every file at it;
- **Review branch** and **Review all** at the top, which review the current branch (`kind: "release"`, for compatibility with saved reviews) and name no revision. The controller resolves the current branch (or HEAD when detached). **Review all** (`scope: "branch"`) reviews every file at its tip. **Review branch** (`scope: "changes"`) diffs from the merge-base with the default branch (`resolveDefaultBranch`: `origin/HEAD`, else `main`, `master`, `origin/main`, `origin/master`), labelled `<default> (merge-base)`. Without a default branch or shared history it fails with a message pointing to Review all; on a branch with no commits beyond the default branch it reports there is nothing to review. A `kind: "release"` request that names a revision is ignored.

**◈ Release › Load range** sends `resolveReleaseRange`, and the panel answers with the highest version tag (`1.5.0` or `v1.5.0`, compared numerically) reachable from HEAD and the current branch, as commit hashes (`resolveReleaseRange` in `services/releaseRange.ts`). The dashboard loads that comparison and nothing more; **Summarize changes** and **Review commit** in the detail toolbar then act on it, and a review is labelled with the tag and branch. Without a reachable release tag, or with no changes since it, the comparison status says so and nothing is loaded.

### Review history

Every completed review is saved by `ReviewHistoryStore` (`reviewHistory.ts`) in workspace state (`repositoryManager.reviewHistory`), keyed by absolute repository root: the result, the report context, the triage and the workspace folder it ran in. Nothing is written to the repository. Each repository keeps its newest 20 reviews; skipped and failed coverage beyond 200 entries is dropped with a note in the limitations. Triage changes update the saved copy. Saving is best effort: a failure leaves the result on screen. The dashboard lists a repository's saved reviews (`listReviewHistory`) under **Past reviews** with date, range, the reviewed commits (base → target for a diff), readiness and counts; the open review's header shows them too, since a label such as a branch name moves on; `openStoredReview` reopens one under a new request id with its triage, so export, evidence and auto-fix work as for a new result (auto-fix still requires the reviewed commit to be checked out), and `deleteStoredReview` removes one.

Before any request, a modal asks for consent to send source to Copilot, with **Start review** and **Always allow for this repository**. "Always allow" is stored in workspace state per repository root (`ReviewConsentStore`); the **Repository Manager: Forget Review Permissions** command lists the allowed repositories, all preselected, and forgets the ones you keep ticked. `repositoryManager.review.confirmBeforeSending` asks before every review again (and then offers only **Start review**). One review runs at a time, and **Cancel** stops it. It runs in the background: the rest of the dashboard stays usable, and only the review buttons are disabled until it ends. Each review is pinned to the workspace folder it started in, and a stored review keeps that folder. Switching folders therefore neither cancels it nor redirects its evidence, export or auto-fix to another repository.

`SecurityReviewService` reports progress as a message plus a `ReviewProgressDetail`: the phase (`planning`, `analyzing`, `verifying`, `finishing`), component *n* of *m*, files done of the planned total, and candidate findings so far; the first detail after planning lists every component and its file count. The Review tab turns this into a progress bar and a component checklist.

Results open in the detail pane's **Review** tab. Readiness is computed by `assessReadiness` in `reviewReport.ts`, the same function the exported report uses:

- **Blocked**: a verified critical or high finding, or a policy `violation`.
- **Needs attention**: hypotheses (most severe first, so an unconfirmed critical finding leads but does not block), verified medium or low findings, `insufficient_evidence` rules, an unconfigured policy when compliance was requested, and incomplete coverage.
- **No blocking findings**: none of the above. This is not a statement that the code is secure.

Triage (`setFindingTriage`) records **Needs fix** or **Dismiss** per finding, with a dismissal reason (`false_positive`, `accepted_risk`, `not_applicable`). `assessReadiness(result, triage)` moves dismissed findings to `dismissed`, where they no longer affect readiness; the report lists them under **Dismissed by reviewer** and records every finding's triage.

## Auto-fix

`ReviewFixService` proposes fixes for the findings marked **Needs fix**. It sends the findings and the current content of the files they cite at the reviewed commit to the selected model, which returns exact `find` → `replace` edits. An edit applies only to a cited file and only when its `find` text occurs exactly once; others are reported as rejected. Each edit names the finding it fixes (or counts for the findings citing its file), so every proposed file lists its findings. While proposing, `propose` reports steps (`checking`, `sending` with the finding, file and request sizes, `receiving` with the characters of the reply so far, `validating`), which the Review tab shows as a checklist with elapsed time. The proposal is shown as a diff per file; **Apply all** writes every file, **Apply selected** only the ticked ones (`applyReviewFix` with `paths`), and the rest stay proposed. Nothing is staged or committed. A finding becomes `fixed` in the triage once every proposed file with edits for it is applied; reviewers can also mark a finding **Fixed** by hand. Fixed findings, like dismissed ones, leave readiness; the report lists them in their own sections, while the dashboard keeps them where they were found, folded to one line with their state and **Undo** (`layout` is the readiness without triage). When a finding in a proposal is no longer marked **Needs fix**, its files leave the proposal and the rest still apply (`reviewFixUpdated`); when another finding is marked, or nothing would be left, the proposal closes with a note that says why (`reviewFixDiscarded` with `message`).

Before asking the model, and again before writing, it checks that HEAD is the reviewed commit, and that the cited files exist, are at most 200 KB, have no staged or unstaged changes and no unsaved editor changes. It also checks that at most 8 files are involved. Apply also refuses if a file changed since the proposal. The same consent as a review applies before code is sent.

Evidence in a two-commit review jumps to the cited line in the dashboard diff; otherwise the file opens read-only at the reviewed revision. The Review tab header and the report title name the kind of review, **Diff: 1.5.0 → main** or **Branch: main**. **Copy Markdown** and **Save report…** export the report with both commits, the policy hash, the model, coverage and limitations. Reviews run in VS Code because the Copilot language-model API is not available in CI.
