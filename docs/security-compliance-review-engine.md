# Security and compliance review engine (MVP 2, W3–W5)

`SecurityReviewService.review(request, token, progress, selectedModelId?)` performs a read-only review of a Git commit. It supports `scope: "changes"` (base → target, with access to other files at target) and `scope: "branch"` (files tracked at target). `categories` can include `security`, `compliance` or both. The `targetSha`, optional `baseSha`, and policy content hash are resolved before requests to the model; changing the checked-out branch does not change a running review.

The survey groups files by component (up to 8 per model request, 256 per run), reports files outside the budget, and loads compliance rules from the policy in the target commit. The model may request bounded `read_file`, `search_code`, `file_exists` and `read_diff` operations; it cannot run shell commands. Review uses the selected Copilot model through the existing VS Code language-model API. Work exceeding model or tool limits is reported as incomplete.

Every returned finding must cite a real file, revision and line. In changes mode, its cited line must be added or removed by the comparison. Compliance evidence must also lie inside the cited rule's scope. A second model request checks candidates for counterevidence, with the rule's description and required evidence for compliance findings: rejected candidates are discarded, uncertain ones remain hypotheses, and a candidate the verifier returns no verdict for is a hypothesis and makes coverage incomplete. Findings for `manual` or `static` rules are never promoted to `verified` by the AI check. A `verified` status means the citation passed mechanical validation **and** the second AI check supported the finding; it is not a proof of exploitability. Review coverage records surveyed, analyzed, skipped and failed files separately and never infers that no vulnerabilities exist from an empty findings list.

Each component is analyzed and verified in turn, and its outcome (kept findings with their status, policy results, partly reviewed files, model notes) is saved by `ReviewUnitCache` (`reviewUnitCache.ts`) in workspace state. The key hashes the model id and version, `PROMPT_VERSION` (a hash of the prompts and the initial content limits), any extra instructions, both commits, scope, categories, the component's paths and its rules, so a saved outcome is reused only when the model would be asked exactly the same thing. Only components with no failed check are saved. At most 300 outcomes are kept, none older than 30 days, newest first. A review run again at the same commits therefore asks only for components that are not saved yet: a review stopped by Cancel, by closing VS Code or by a model error continues where it left off.

Cancel stops after the current step. When at least one component finished, the result is returned with `partial: { unitsDone, unitsTotal }`, incomplete coverage and a limitation saying where it stopped; the dashboard shows and saves it like a finished review, with **Continue review**. Cancelled before any component finished, the review fails as cancelled. A review superseded by another one, or by closing the panel, is dropped as before.

Model notes become `toVerify`: what someone should check by hand, such as callers or CI settings outside the scope. `consolidateLimitations` keeps each note whole (a sentence like "the severity depends on that configuration" stays with the one before it), drops restatements the report already makes (which files were in scope, that they contain no sinks, that no flaw was found, that a file was not read, truncation), keeps a "was not read" sentence only beside a point it explains, and never re-capitalizes file names. `limitations` keeps the tool's own notes. Coverage is summarized once (`summarizeCoverage`) as fully reviewed, partly reviewed (with lockfiles, images, diagrams and test inputs counted apart), not reviewed and failed checks.

Compliance rules with `verification: "manual"` or `"static"` are marked `insufficient_evidence` until their corresponding evidence or scanner exists. Missing policy is `not_configured`. A rule the model judges not applicable in every reviewed batch is `not_applicable`. A rule cannot pass when applicable files or checks fail or exceed the review budget. Security review does not require a policy. Dependency vulnerability databases and build/test execution are outside the engine.

### Failed checks, the log, and running a review again

A failed check is part of a review that did not complete. A component the model could not review (the files do not fit its context, the request failed) lists each of its files with the reason. A component whose answer did not pass a check lists the component once: a finding citing lines that are not in the reviewed files, more than 20 findings, a finding the second check gave no verdict for, a missing policy result. The result's `log` keeps progress steps with their time, plus one line per failed reason and component. It holds at most 400: every failure, then the newest steps (`trimReviewLog`). Several bad findings from one component count as one failed check. The Review tab groups failed checks by reason with what to do, and **Retry failed** runs the same review again. Components that passed come from `ReviewUnitCache`, so only the failed ones are asked again. A stored review keeps failures before skipped files, and the failures and the end of a long log (`MAX_STORED_LOG`).

### Decisions carried from earlier reviews

Each finding has a `fingerprint`: a hash of its category, rule, file and the text of its first cited lines. It is not a hash of the model's wording, so a re-run that phrases the finding differently gets the same fingerprint, while an edit to the cited code gives a new one. When a review completes, `carryTriage` (`reviewTriageCarry.ts`) looks up the repository's saved reviews, newest first:

- a finding dismissed earlier is dismissed again, with the same reason;
- one marked **Needs fix** stays so;
- one marked **Fixed** and reported again on unchanged code becomes **Needs fix**, labelled "Reported again after Fixed".

A fingerprint alone is not enough, because two issues can cite the same line (a secret and an injection). A decision carries only when `sameIssue` also holds: no differing skills, and the explanations share at least a quarter of their key words. It also requires that exactly one earlier finding matches. The newest saved review that contains the finding decides, so a decision undone there is not revived from an older review. Carried decisions record the earlier review's date in `carried`, and the dashboard labels them "earlier review". Components reused from the cache get fingerprints when they are reused, while reviews saved before fingerprints existed carry nothing. **Retry failed** repeats the reviewed repository, workspace folder and model, not the ones the dashboard shows now.

## Review skills and clean code

A review skill is a short checklist sent to the model with the files it applies to. The extension ships nine in `resources/review-skills/`, written for this extension from public standards and naming them in `references`: injection and dangerous sinks (CWE Top 25, OWASP ASVS 5.0), authentication and sessions (ASVS), secrets and cryptography (Microsoft SDL, ASVS), CI/CD and supply chain (OpenSSF Scorecard, SLSA), cloud and infrastructure as code (AWS Well-Architected Security Pillar), Python and JavaScript/TypeScript (Amazon Q detector library categories, CWE), C and C++ (SEI CERT, C++ Core Guidelines, Microsoft SDL banned functions, CWE memory-safety entries), and clean code (Google's code review guide). A skill file is Markdown with a header between `---` lines: `id`, `name`, `category` (`security` or `quality`), `appliesTo` (a JSON array of globs) and optional `references`, then the guidance (`parseReviewSkill` in `services/reviewSkills.ts`).

`ReviewSkillStore` (`reviewSkillStore.ts`) adds the skills a user imports from a Markdown file (at most 30, 6,000 characters of guidance each; one with a bundled id replaces it) and the ones turned off, both in global state. Skills are never read from the reviewed repository: the prompt treats them as trusted guidance, and repository content stays untrusted. For each component, `selectReviewSkills` picks the enabled skills whose globs match one of its paths, ignoring case (policy scopes stay case-sensitive), security skills when `security` is reviewed and quality skills when `quality` is, up to 8,000 characters. When they do not all fit, security skills go first, then those matching more of the component's files; clean code gives way first, and a skill that does not fit is reported as left out. `injection-sinks` names kinds of sink and each language skill names its APIs, so two skills do not describe the same line. The guidance counts against the component's first-request budget (`INITIAL_UNIT_CHARS`), so less source is sent up front rather than a component growing past the model's limit. A hash of each skill sent (id, name, category, guidance) is part of the component's cache key, so turning a skill off or changing one asks the model again for the components it applied to. The result lists the skills per component (`skillsApplied`), and a finding may name the skill that led to it (`skill`, kept only when that skill was sent for its component). A finding from a quality skill is a quality finding whatever category the model gave it.

`categories` may also include `quality` (the dashboard's **Clean code** checkbox, off by default and remembered in global state). Without a policy, a compliance request ends early only when compliance is the only category. Quality findings cover maintainability: complexity, duplication, naming, error handling, dead code and tests. Their severity is at most medium, they go through the same evidence and second-check rules, and `assessReadiness` keeps them in their own `quality` list: they never make a review blocked or needing attention. The report has a **Code quality** section and a **Review skills** section.

## Dashboard and release review (W6–W7)

`ReviewController` connects the engine to the dashboard. A review is a diff (`scope: "changes"`) or every file at a commit (`scope: "branch"`); each starts at once with both categories and the model selected for AI summaries; there is no dialog. The entry points are:

- **Review commit**, first in the review group next to **Load range**: the changes the detail pane shows (the selected commit against its parent, or the loaded Base/Target selection, branch comparison or release range);
- **Review changes**, first in the group: the local changes, staged and unstaged and new files that `.gitignore` does not exclude (`kind: "local"`, no revisions). The controller takes a snapshot (`snapshotLocalChanges` in `services/localChangesSnapshot.ts`): a temporary index copied from the real one, `git add -A`, `write-tree`, and `commit-tree` with HEAD as parent, a fixed identity and HEAD's date. HEAD, refs, the index and the working tree are untouched, and nothing points to the snapshot, so Git prunes it like any unreachable object (after `gc.pruneExpire`, two weeks by default): a saved review of local changes keeps its findings, but its evidence can no longer open the snapshot after that. The review is then HEAD → snapshot, labelled `HEAD → local changes`; the same changes give the same snapshot, so running it again reuses saved components and triage. It fails with a message when there is nothing to review or no first commit. The consent question says that uncommitted code and new files are sent, and that clean filters the user's Git config sets for those files run while the snapshot is taken (as they do for `git status`). Retry runs the same snapshot again as a local review (both ends given). The button is always available: whether there is anything to review is decided when the snapshot is taken, not from the dashboard's last refresh. Auto-fix is not offered for these reviews: it only writes files that have no local changes;
- the history menu: a commit against its parent, or every file at it;
- **Review branch** and **Review all**, after it, which review the current branch (`kind: "release"`, for compatibility with saved reviews) and name no revision. The controller resolves the current branch (or HEAD when detached). **Review all** (`scope: "branch"`) reviews every file at its tip. **Review branch** (`scope: "changes"`) diffs from the merge-base with the default branch (`resolveDefaultBranch`: `origin/HEAD`, else `main`, `master`, `origin/main`, `origin/master`), labelled `<default> (merge-base)`. Without a default branch or shared history it fails with a message pointing to Review all; on a branch with no commits beyond the default branch it reports there is nothing to review. A `kind: "release"` request that names a revision is ignored.

**◈ Release › Load range** sends `resolveReleaseRange`, and the panel answers with the highest version tag (`1.5.0` or `v1.5.0`, compared numerically) reachable from HEAD and the current branch, as commit hashes (`resolveReleaseRange` in `services/releaseRange.ts`). The dashboard loads that comparison and nothing more; **Summarize changes** in the detail toolbar and **Review commit** next to it then act on it, and a review is labelled with the tag and branch. Without a reachable release tag, or with no changes since it, the comparison status says so and nothing is loaded.

### Review history

Every completed review is saved by `ReviewHistoryStore` (`reviewHistory.ts`) in workspace state (`repositoryManager.reviewHistory`), keyed by absolute repository root: the result, the report context, the triage and the workspace folder it ran in. Nothing is written to the repository. Each repository keeps its newest 20 reviews; skipped and failed coverage beyond 200 entries is dropped with a note in the limitations. Triage changes update the saved copy. Saving is best effort: a failure leaves the result on screen. The review tab lists the saved reviews of the dashboard's repository (`listReviewHistory`) under **Past reviews** with date, range, the reviewed commits (base → target for a diff), readiness and counts; the open review's header shows them too, since a label such as a branch name moves on; `openStoredReview` reopens one under a new request id with its triage, so export, evidence and auto-fix work as for a new result (auto-fix still requires the reviewed commit to be checked out), and `deleteStoredReview` removes one.

Before any request, a modal asks for consent to send source to Copilot, with **Start review** and **Always allow for this repository**. "Always allow" is stored in workspace state per repository root (`ReviewConsentStore`); the **Repository Manager: Forget Review Permissions** command lists the allowed repositories, all preselected, and forgets the ones you keep ticked. `repositoryManager.review.confirmBeforeSending` asks before every review again (and then offers only **Start review**). One review runs at a time, and **Cancel** stops it. It runs in the background: the rest of the dashboard stays usable, and only the review buttons are disabled until it ends. Each review is pinned to the workspace folder it started in, and a stored review keeps that folder. Switching folders therefore neither cancels it nor redirects its evidence, export or auto-fix to another repository.

`SecurityReviewService` reports progress as a message plus a `ReviewProgressDetail`: the phase (`planning`, `analyzing`, `verifying`, `finishing`), component *n* of *m*, files done of the planned total, and candidate findings so far; the first detail after planning lists every component and its file count. The Review tab turns this into a progress bar and a component checklist.

Results open in the **Repository Review** editor tab (`resources/review.js`), a webview of its own beside the dashboard. `ReviewBridge` (`src/reviewBridge.ts`) routes the messages: the dashboard asks for a review (`requestReview`), the bridge opens the tab and hands it the request once the tab reports `reviewReady`, the tab sends `startReview` and the rest to `ReviewController`, and the controller's messages go to the tab. The dashboard publishes its repository, folder and model (`dashboardContext`) and the tab follows it: switching repository closes a finished review of another repository (also when the tab opens again) and lists the new one's past reviews, kept per folder and repository. `startReview` carries the folder the review was asked in; if the dashboard switched folders before the tab started it, the controller refuses it rather than resolve its relative path in another folder. Closing the tab does not stop a review. The bridge keeps the messages of the review the tab showed and replays them (`reviewRestore`) when the tab opens again; only an auto-fix proposal is discarded, since it lives on screen. The dashboard's **Review ↗** button shows `reviewStatus`: the percentage while a review runs, then the number of blocking items. Readiness is computed by `assessReadiness` in `reviewReport.ts`, the same function the exported report uses:

- **Blocked**: a verified critical or high finding, or a policy `violation`.
- **Needs attention**: hypotheses (most severe first, so an unconfirmed critical finding leads but does not block), verified medium or low findings, `insufficient_evidence` rules, an unconfigured policy when compliance was requested, and incomplete coverage.
- **No blocking findings**: none of the above. This is not a statement that the code is secure.

Triage (`setFindingTriage`) records **Needs fix** or **Dismiss** per finding, with a dismissal reason (`false_positive`, `accepted_risk`, `not_applicable`). `assessReadiness(result, triage)` moves dismissed findings to `dismissed`, where they no longer affect readiness; the report lists them under **Dismissed by reviewer** and records every finding's triage.

## Auto-fix

`ReviewFixService` proposes fixes for the findings marked **Needs fix**. It sends the findings and the current content of the files they cite at the reviewed commit to the selected model, which returns exact `find` → `replace` edits. An edit applies only to a cited file and only when its `find` text occurs exactly once; others are reported as rejected. Each edit names the finding it fixes (or counts for the findings citing its file), so every proposed file lists its findings. While proposing, `propose` reports steps (`checking`, `sending` with the finding, file and request sizes, `receiving` with the characters of the reply so far, `validating`), which the Review tab shows as a checklist with elapsed time. The proposal is shown as a diff per file; **Apply all** writes every file, **Apply selected** only the ticked ones (`applyReviewFix` with `paths`), and the rest stay proposed. Nothing is staged or committed. A finding becomes `fixed` in the triage once every proposed file with edits for it is applied; reviewers can also mark a finding **Fixed** by hand. Fixed findings, like dismissed ones, leave readiness; the report lists them in their own sections, while the review tab keeps them where they were found, folded to one line with their state and **Undo** (`layout` is the readiness without triage). When a finding in a proposal is no longer marked **Needs fix**, its files leave the proposal and the rest still apply (`reviewFixUpdated`); when another finding is marked, or nothing would be left, the proposal closes with a note that says why (`reviewFixDiscarded` with `message`).

Before asking the model, and again before writing, it checks that HEAD is the reviewed commit, and that the cited files exist, are at most 200 KB, have no staged or unstaged changes and no unsaved editor changes. It also checks that at most 8 files are involved. Apply also refuses if a file changed since the proposal. The same consent as a review applies before code is sent.

Evidence in a two-commit review of the dashboard's repository brings the dashboard forward and jumps to the cited line in its diff (`showReviewEvidence`); otherwise the file opens read-only at the reviewed revision. The Review tab header and the report title name the kind of review, **Diff: 1.5.0 → main** or **Branch: main**. **Copy Markdown** and **Save report…** export the report with both commits, the policy hash, the model, coverage and limitations. Reviews run in VS Code because the Copilot language-model API is not available in CI.
