# Security and compliance review engine (MVP 2, W3–W5)

`SecurityReviewService.review(request, token, progress, selectedModelId?)` performs a read-only review of a Git commit. It supports `scope: "changes"` (base → target, with access to other files at target) and `scope: "branch"` (files tracked at target). `categories` can include `security`, `compliance` or both. The `targetSha`, optional `baseSha`, and policy content hash are resolved before requests to the model; changing the checked-out branch does not change a running review.

The survey groups files by component (up to 8 per model request, 256 per run), reports files outside the budget, and loads compliance rules from the policy in the target commit. The model may request bounded `read_file`, `search_code`, `file_exists` and `read_diff` operations; it cannot run shell commands. Review uses the selected Copilot model through the existing VS Code language-model API. Work exceeding model or tool limits is reported as incomplete.

Every returned finding must cite a real file, revision and line. In changes mode, its cited line must be added or removed by the comparison. Compliance evidence must also lie inside the cited rule's scope. A second model request checks candidates for counterevidence, with the rule's description and required evidence for compliance findings: rejected candidates are discarded, uncertain ones remain hypotheses, and a candidate the verifier returns no verdict for is a hypothesis and makes coverage incomplete. Findings for `manual` or `static` rules are never promoted to `verified` by the AI check. A `verified` status means the citation passed mechanical validation **and** the second AI check supported the finding; it is not a proof of exploitability. Review coverage records surveyed, analyzed, skipped and failed files separately and never infers that no vulnerabilities exist from an empty findings list.

Compliance rules with `verification: "manual"` or `"static"` are marked `insufficient_evidence` until their corresponding evidence or scanner exists. Missing policy is `not_configured`. A rule the model judges not applicable in every reviewed batch is `not_applicable`. A rule cannot pass when applicable files or checks fail or exceed the review budget. Security review does not require a policy. Dependency vulnerability databases and build/test execution are outside the engine.

## Dashboard and release review (W6–W7)

`ReviewController` connects the engine to the dashboard. The reviews are **Review changes** (`scope: "changes"`) and **Review branch** (`scope: "branch"`); each starts at once with both categories and the model selected for AI summaries; there is no dialog. The entry points are the detail toolbar, which also holds **Summarize changes** and reviews the changes the detail pane shows (the selected commit against its parent, or the loaded Base/Target selection, branch comparison or release range), the history menu (the commit against its parent, or every file at it) and **◈ Release › Review branch**. A release review names no revision: the controller reviews every file on the current branch (or HEAD when detached) and reports the label back to the Review tab. The controller accepts only `scope: "branch"` for `kind: "release"`.

**◈ Release › Load range** sends `resolveReleaseRange`, and the panel answers with the highest version tag (`1.5.0` or `v1.5.0`, compared numerically) reachable from HEAD and the current branch, as commit hashes (`resolveReleaseRange` in `services/releaseRange.ts`). The dashboard loads that comparison and nothing more; **Summarize changes** and **Review changes** in the detail toolbar then act on it, and a review is labelled with the tag and branch. Without a reachable release tag, or with no changes since it, the comparison status says so and nothing is loaded.

### Review history

Every completed review is saved by `ReviewHistoryStore` (`reviewHistory.ts`) in workspace state (`repositoryManager.reviewHistory`), keyed by absolute repository root: the result, the report context, the triage and the workspace folder it ran in. Nothing is written to the repository. Each repository keeps its newest 20 reviews; skipped and failed coverage beyond 200 entries is dropped with a note in the limitations. Triage changes update the saved copy. Saving is best effort: a failure leaves the result on screen. The dashboard lists a repository's saved reviews (`listReviewHistory`) under **Past reviews** with date, range, the reviewed commits (base → target for a diff), readiness and counts; the open review's header shows them too, since a label such as a branch name moves on; `openStoredReview` reopens one under a new request id with its triage, so export, evidence and auto-fix work as for a new result (auto-fix still requires the reviewed commit to be checked out), and `deleteStoredReview` removes one.

Before any request, a modal asks for consent to send source to Copilot, with **Start review** and **Always allow for this repository**. "Always allow" is stored in workspace state per repository root (`ReviewConsentStore`); the **Repository Manager: Forget Review Permissions** command lists the allowed repositories, all preselected, and forgets the ones you keep ticked. `repositoryManager.review.confirmBeforeSending` asks before every review again (and then offers only **Start review**). One review runs at a time, and **Cancel** stops it. It runs in the background: the rest of the dashboard stays usable, and only the review buttons are disabled until it ends. Each review is pinned to the workspace folder it started in, and a stored review keeps that folder. Switching folders therefore neither cancels it nor redirects its evidence, export or auto-fix to another repository.

`SecurityReviewService` reports progress as a message plus a `ReviewProgressDetail`: the phase (`planning`, `analyzing`, `verifying`, `finishing`), component *n* of *m*, files done of the planned total, and candidate findings so far; the first detail after planning lists every component and its file count. The Review tab turns this into a progress bar and a component checklist.

Results open in the detail pane's **Review** tab. Readiness is computed by `assessReadiness` in `reviewReport.ts`, the same function the exported report uses:

- **Blocked**: a verified critical or high finding, or a policy `violation`.
- **Needs attention**: hypotheses (most severe first, so an unconfirmed critical finding leads but does not block), verified medium or low findings, `insufficient_evidence` rules, an unconfigured policy when compliance was requested, and incomplete coverage.
- **No blocking findings**: none of the above. This is not a statement that the code is secure.

Triage (`setFindingTriage`) records **Needs fix** or **Dismiss** per finding, with a dismissal reason (`false_positive`, `accepted_risk`, `not_applicable`). `assessReadiness(result, triage)` moves dismissed findings to `dismissed`, where they no longer affect readiness; the report lists them under **Dismissed by reviewer** and records every finding's triage.

## Auto-fix

`ReviewFixService` proposes fixes for the findings marked **Needs fix**. It sends the findings and the current content of the files they cite at the reviewed commit to the selected model, which returns exact `find` → `replace` edits. An edit applies only to a cited file and only when its `find` text occurs exactly once; others are reported as rejected. Each edit names the finding it fixes (or counts for the findings citing its file), so every proposed file lists its findings. While proposing, `propose` reports steps (`checking`, `sending` with the finding, file and request sizes, `receiving` with the characters of the reply so far, `validating`), which the Review tab shows as a checklist with elapsed time. The proposal is shown as a diff per file; **Apply all** writes every file, **Apply selected** only the ticked ones (`applyReviewFix` with `paths`), and the rest stay proposed. Nothing is staged or committed. A finding becomes `fixed` in the triage once every proposed file with edits for it is applied; reviewers can also mark a finding **Fixed** by hand. Fixed findings, like dismissed ones, leave readiness and get their own section in the dashboard and the report.

Before asking the model, and again before writing, it checks that HEAD is the reviewed commit, and that the cited files exist, are at most 200 KB, have no staged or unstaged changes and no unsaved editor changes. It also checks that at most 8 files are involved. Apply also refuses if a file changed since the proposal. The same consent as a review applies before code is sent.

Evidence in a two-commit review jumps to the cited line in the dashboard diff; otherwise the file opens read-only at the reviewed revision. The Review tab header and the report title name the kind of review, **Diff: 1.5.0 → main** or **Branch: main**. **Copy Markdown** and **Save report…** export the report with both commits, the policy hash, the model, coverage and limitations. Reviews run in VS Code because the Copilot language-model API is not available in CI.
